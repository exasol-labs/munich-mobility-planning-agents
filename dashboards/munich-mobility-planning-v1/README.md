# munich-mobility-planning-v1: Today, per resident

**Question:** how well is each Munich district served by scheduled public transport today, per resident?

**URL once deployed:** http://127.0.0.1:5100/apps/munich-mobility-planning-v1 · tutorial chapter: [04-v1-residents.md](../../tutorial/04-v1-residents.md)

One map, no controls. Each district is coloured by the scheduled places offered on a typical weekday per 1,000 residents, divided by the Munich average.

## What it shows (top to bottom)

1. **Header:** eyebrow "Urban planning", title "Munich Mobility Planning", subtitle "v1 – Today, per resident".
2. **Intro card** (verbatim):
   > **How well is each district served by public transport today?**
   > The map compares the scheduled capacity of buses, trams, U-Bahn and S-Bahn (the places offered on a typical weekday) with the number of people living in each district. 1.0× is the Munich average. Red districts get fewer places per resident than average, blue ones more. The outlined districts are the densest third.
3. **Service map** "How well served is each district? – today" (640 px high):
   - A choropleth of the 25 districts, coloured by `service_ratio`. The scale is log2, centred on 1.0× and clamped to 0.4–2.5. Values below 1 are orange, values above 1 are blue, and 1.0 is grey (`#dedcd6`). The colour bar is titled "× city average", with ticks at 0.5, 0.75, 1, 1.5 and 2.
   - A thick dark outline on the **densest third** (`is_dense = 1`). Its legend entry reads "dense (top third by residents per km²)".
   - A text label at each district centroid with the short name and the unclamped ratio, e.g. "Altstadt-Lehel 6.18×". The label shows the real value even when the colour is clamped at 2.5.
   - Hover: the ratio, residents, residents per km², places and departures per 1,000 residents, residents per station, and the mode note ("mostly bus", "mostly rail" or "mixed").
   - Base map `carto-positron`, centred on 48.152 N, 11.548 E, zoom 9.85.
4. **Caveat line** under the map: "Scheduled service (MVV timetable, reference Wednesday 21 Oct 2026), not passengers or delays. Residents: end of 2024."
5. **"SQL executed" foldout** at the very bottom, folded by default. The header reads e.g. "SQL executed · 2 statements for this view · 1.2 s". Each entry shows the file, its purpose, the parameters, the rows, the duration (or "cached, ran at HH:MM:SS"), and an inner fold-out with the full SQL as sent to Exasol.

## How it computes

All SQL is in `queries/ranking.sql`. Placeholders use pyexasol syntax (`{year!d}`, `{w_jobs!f}`, `{projects!s}`). The parts v1 relies on:

**1. The reference weekday:** pinned to Wednesday 21 Oct 2026, inside the GTFS feed (1 Sep–30 Nov 2026). Then the service ids that run on that day.

```sql
WITH feed AS (
    SELECT MIN("start_date") AS f_start, MAX("end_date") AS f_end FROM MUNICH_DATASET.MVV_CALENDAR
),
base AS (SELECT LEAST(GREATEST(DATE '2026-10-21', f_start), ADD_DAYS(f_end, -6)) AS b FROM feed),  -- reference weekday pinned: Wed 21 Oct 2026
rd AS (SELECT ADD_DAYS(b, MOD(7 - MOD(DAYS_BETWEEN(b, DATE '1970-01-07'), 7), 7)) AS ref_date FROM base),
svc AS (
    SELECT c."service_id" FROM MUNICH_DATASET.MVV_CALENDAR c CROSS JOIN rd
    WHERE c."wednesday" = 1 AND rd.ref_date BETWEEN c."start_date" AND c."end_date"
      AND c."service_id" NOT IN (SELECT x."service_id" FROM MUNICH_DATASET.MVV_CALENDAR_DATES x CROSS JOIN rd r2
                                 WHERE x."date" = r2.ref_date AND x."exception_type" = 2)
    UNION
    SELECT x."service_id" FROM MUNICH_DATASET.MVV_CALENDAR_DATES x CROSS JOIN rd
    WHERE x."date" = rd.ref_date AND x."exception_type" = 1
),
```

Run on or just before 21 Oct 2026, this gives Wednesday 21 Oct 2026, the day the reference numbers were taken on. On another date you get another Wednesday in the feed, and the numbers can differ slightly.

**2. Capacity per trip:** the `LINE_CAPACITY` override for the line if there is one, else `VEHICLE_CAPACITY` by `line_mode` (S-Bahn 1,200, U-Bahn 900, regional rail 500, tram 205, bus 90).

```sql
lines AS (
    SELECT r."route_id", r."route_short_name" AS line, COALESCE(lc."capacity_per_trip", v."capacity_per_trip") AS capacity
    FROM MUNICH_DATASET.MVV_ROUTES r
    JOIN MUNICH_DATASET.VEHICLE_CAPACITY v ON v."line_mode" = r."line_mode"
    LEFT JOIN MUNICH_DATASET.LINE_CAPACITY lc ON lc."line" = r."route_short_name" AND lc."line_mode" = r."line_mode"
),
wt AS (
    SELECT t."trip_id", l.line, l.capacity
    FROM MUNICH_DATASET.MVV_TRIPS t JOIN svc ON svc."service_id" = t."service_id"
    JOIN lines l ON l."route_id" = t."route_id"
),
```

**3. Supply: places offered = departures × capacity per trip.** Every scheduled stop event on the reference Wednesday counts once, in the district of its stop, at stops inside Munich only. This leaves out the 24,218 stops with `in_munich = 0`.

```sql
dep AS (
    SELECT s."district_no" AS dno, COUNT(*) AS departures, SUM(wt.capacity) AS places, COUNT(DISTINCT wt.line) AS n_lines
    FROM MUNICH_DATASET.MVV_STOP_TIMES st
    JOIN wt ON wt."trip_id" = st."trip_id"
    JOIN MUNICH_DATASET.MVV_STOPS s ON s."stop_id" = st."stop_id"
    WHERE s."in_munich" = 1
    GROUP BY s."district_no"
),
```

**4. Demand:** residents. At `year = 2024` the interpolation below returns `pop_2024` (the end-2024 count), and at `w_jobs = 0` the activity is residents only.

```sql
           p."pop_2024" + (p."pop_2045_forecast" - p."pop_2024") * ({year!d} - 2024) / 21.0 AS pop_y,
```
```sql
           dem.pop_y + {w_jobs!f} * dem.jobs_y AS activity,
```

**5. The ratio the map shows:** a district's places per 1,000 activity, divided by the city average. The city average is total places ÷ total activity, not a mean of district ratios.

```sql
           1000.0 * SUM(places_today) OVER () / SUM(activity_24) OVER () AS city_places_per_1k_act_24,
```
```sql
       ROUND(places_per_1k_act / city_places_per_1k_act_24, 3) AS service_ratio,
```

**6. The dense outline:** the top third of districts by activity per km². At w = 0 that is residents per km².

```sql
           NTILE(3) OVER (ORDER BY activity_per_km2 DESC, population DESC) AS act_t,
```
```sql
       CASE WHEN act_t = 1 THEN 1 ELSE 0 END AS is_dense,
```

**7. The mode note in the hover:** it compares a district's rank by places with its rank by departures. If a district ranks much higher by departures than by places, its service is mostly small vehicles (bus), and the other way round means mostly rail.

```sql
       CASE WHEN places_rank - dep_rank > 5 THEN 'mostly bus'
            WHEN dep_rank - places_rank > 5 THEN 'mostly rail' ELSE '' END AS mode_note,
```

The parts of `ranking.sql` about projects (`need`, `pl`, `ev_sel`, `ana`, `laim`, `sb`, `ps`, `pmeta`, `comps`, `sel`) add nothing when `projects = 'none'`. v4 uses them.

**The colour,** in `app.py`: the ratio is clamped to 0.4–2.5 and mapped to log2, so 0.5× and 2× are equally far from grey.

```python
    z = [math.log2(min(max(v, RATIO_LO), RATIO_HI)) for v in ratio]
```

**geo.sql:**

```sql
SELECT "district_no" AS district_no, "district_name" AS district, "centroid_lat" AS centroid_lat, "centroid_lon" AS centroid_lon,
       "polygon_wkt" AS polygon_wkt
FROM MUNICH_DATASET.DISTRICTS
ORDER BY "district_no"
```

`app.py` turns the WKT into GeoJSON itself (`wkt_to_geometry`), so the app needs no GIS library. Query results are cached for an hour (`CACHE_TTL_S = 3600`).

## What it can't tell you

The MVV data is the **scheduled** timetable: no passengers, crowding, delays or live traffic. Capacities are planning values per mode or line, not measured loads. A district can look well served because rail lines pass through it, even if many of its residents live far from a station.
